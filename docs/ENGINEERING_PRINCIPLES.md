# CareerOS Engineering Principles

**Status: permanent.** These rules bind every future contributor, human or AI.
Follow them unless a revision is explicitly recorded in
[DECISION_LOG.md](./DECISION_LOG.md). When code and this document disagree,
either fix the code or record a decision — never silently diverge.

Related: [PRODUCT_VISION.md](./PRODUCT_VISION.md) ·
[ARCHITECTURE.md](./ARCHITECTURE.md) · [DECISION_LOG.md](./DECISION_LOG.md)

---

## 1. The Career Brain is the canonical source of truth

All personal career data — profile, experiences, achievements, skills,
education, projects, certifications, career goals — lives in the Career Brain
tables (`lib/db/schema.ts`, section 1). Everything else **derives** from it:

- Resumes are immutable snapshots selected *from* the Brain (`resume_versions`),
  never hand-edited documents.
- Cover letters are composed *from* Brain facts (`cover_letter_versions`).
- Fit scores compare a job *against* the Brain (`lib/scoring/`).
- Future systems (AI Coach, analytics, autofill) must ground in the Brain too.

Corollaries:

- New career information enters the Brain through explicit user input — the
  Career Brain editor, the suggestions flow, or the onboarding import flow
  (itself the same reviewed propose → confirm → `commitImport()` path as the
  standalone Import feature) — never as a side effect.
- Improvements discovered while tailoring an artifact (e.g. a better-worded
  bullet) are promoted **back into the Brain**, not stranded in the artifact.
- A derived artifact must record *what* it derived (see `ResumeContent`:
  achievement/skill/experience IDs are captured in each version's snapshot).

## 2. Engines over page logic

Business logic lives in reusable modules under `lib/` ("engines"), never in
pages, route handlers, or components:

| Engine | Location | Consumers today |
|---|---|---|
| Resume | `lib/resume/` | resumes API/UI, job page |
| Cover letter | `lib/coverletter/` | cover-letter API/UI, job page |
| Career Match | `lib/scoring/` | score API, extension analyze, jobs list, job page, board |
| Suggestions | `lib/suggestions.ts` | suggestions API, dashboard, job page, extension |
| AI providers | `lib/ai/` | resume, cover letter, scoring enhancement |
| Text matching | `lib/text.ts` | resume + cover-letter selection |

Route handlers validate input (zod via `lib/api.ts`), call an engine, and
shape the response. Pages read the DB / call engines and render. If a second
consumer for some logic appears, extract the engine *first*.

## 3. Local-first is a product requirement, not a deployment option

- The app runs entirely on the user's machine: `npm run dev` with an empty
  `.env` must always produce a fully functional product.
- The server binds `127.0.0.1` only. Nothing listens on the network.
- Zero recurring infrastructure. No telemetry. No accounts. No cloud sync.
- The full application state is two directories — the SQLite file and
  `storage/` — that the user can copy, back up, or move at will
  (`npm run backup`, `npm run export`).

## 4. Data portability

- SQLite is accessed exclusively through Drizzle ORM; keep the schema within
  Drizzle's portable subset so a future Postgres (or other) target remains a
  configuration change, not a rewrite.
- Schema changes are additive migrations (`lib/db/migrations/`), generated by
  `drizzle-kit`, applied automatically at connection time (`lib/db/index.ts`).
- `npm run export` must keep producing a complete, human-readable export as
  the schema grows: when you add a table, add it to `scripts/export.ts`.

## 5. AI is optional, replaceable, auditable — and never authoritative

- **Optional:** every AI feature is gated on `config.ai.enabled` (key
  presence). With no key, the product is complete — features degrade to their
  deterministic behavior or hide, they never break.
- **Replaceable:** providers are plain-`fetch` adapters behind one interface
  (`lib/ai/index.ts` → `aiComplete`). No provider SDKs. Adding a provider is
  one adapter file.
- **Auditable:** `aiComplete` is the only outbound-calling function in the
  codebase, and it unconditionally writes an `ai_generations` audit row
  (purpose, provider, model, prompt summary, sizes, timestamp). Never call a
  provider around it.
- **Never authoritative:**
  - AI may improve wording, summarize, explain, rank, and coach.
  - AI must never fabricate experience, skills, certifications, education,
    achievements, or metrics. Prompts state this; parsers enforce it by
    deriving output only from supplied facts and falling back to the
    deterministic result on any parse failure.
  - AI must never change a computed number. The Career Match Engine's scores
    are copied from the deterministic report by construction
    (`lib/scoring/enhance.ts` only merges the seven reasoning strings).
  - Only content the user explicitly acts on is ever sent; no background AI.

## 6. Deterministic core

Scoring, selection, and composition are deterministic: same Brain + same job
→ same output, offline. AI layers on top as an *enhancement pass* with a
guaranteed fallback. New intelligence features follow the same shape:
deterministic baseline first, optional AI refinement second.

## 7. Desktop-first distribution (permanent rule)

CareerOS will eventually ship as a desktop application (Tauri or equivalent)
for non-technical users. **No production feature may require command-line
interaction** — every change must keep the desktop path cheap:

- **No CLI requirements outside development.** Any capability a user needs
  (backup, export, token setup, migrations, diagnostics) must exist — or be
  trivially exposable — through the UI/API. Dev scripts may wrap those code
  paths, but the logic lives in `lib/`, not in the script. Concretely, the
  following must all stay adapter-compatible and UI-reachable: **export,
  backup, notifications, AI providers, browser-extension communication,
  calendar providers, and future OS integrations.**
- **Platform-specific logic is isolated behind adapters.** Every path on disk
  resolves through `config.paths` (`lib/config.ts`) — a desktop build
  repoints one value (the root) at the platform app-data directory.
  Capability-specific behavior (notification delivery, calendar sync,
  messaging) is defined once as an interface in `lib/plugins/types.ts` and
  implemented per platform; engines call the interface, never a concrete
  platform API directly.
- **Business logic is UI-independent.** Engines take data in, return data
  out; they don't import React, Next, browser globals (`window`, `document`,
  `localStorage`), or anything request-scoped. The web UI is one consumer; a
  desktop shell will be another.
- **Avoid web-server-only assumptions.** Prefer capabilities that work in an
  embedded/localhost context; anything that assumes a public origin, external
  DNS, or multi-user semantics is off-architecture.

## 8. User data ownership is first-class

- The user can see where their data lives (Settings page shows the absolute
  paths), copy it, export it losslessly, and delete it.
- Nothing leaves the machine except explicit AI calls (see §5) — and the
  audit log shows exactly what did.
- Extension endpoints are bearer-token gated (`lib/settings.ts`) so arbitrary
  websites can't read or write local data; any route reachable cross-origin
  must enforce the token when the request is cross-origin.

## 9. Working discipline

- Verify before committing: typecheck, production build, and an end-to-end
  exercise of the changed flow on a fresh database.
- Commit per coherent milestone with messages that describe behavior.
- Document major decisions in [DECISION_LOG.md](./DECISION_LOG.md) as they
  are made. Roadmap ideas go to the README/vision doc, not into code.

## 10. Version-first development (permanent rule)

CareerOS is planned in semantic versions (v1.0, v1.1, v1.2, ...), not
isolated feature milestones. A milestone describes *how* a wave of work is
sequenced; a version describes *what a user actually receives* — the two
are not the same, and roadmap documents must speak in versions.

Before proposing or accepting a feature, answer all four questions:

1. Does it improve the **first-time experience** (a new user with an empty
   Career Brain)?
2. Does it improve the **everyday workflow** (a returning user tracking
   applications)?
3. Does it improve **long-term maintainability** (a future contributor,
   human or AI, extending the system)?
4. Is it **appropriate for the current version**, or should it wait for a
   later one?

A feature that fails to improve any of the first three is a candidate for
cutting, not building. A feature that passes 1–3 but fails 4 goes on the
roadmap for a later version instead of being built now — scope creep into
the current version is exactly the failure mode this rule exists to catch.

The intended scope of each version — v1.0 through the long-term roadmap —
is maintained in [IMPLEMENTATION_GUIDE.md](./IMPLEMENTATION_GUIDE.md)'s
**Version Roadmap** section, kept current as versions ship (mirrored briefly
in `README.md` for users). A version is "done" when its roadmap section's
items are shipped and verified, not when an arbitrary time passes.
